## 1. 지금 바로 반영 가능 — 영상 검증으로 근거 확보됨

### 1-1. 차선 샘플 영역 / 평가행 조합 변경 (권장)

**현재값**
```yaml
lane:
  y_lo: 270
  y_hi: 425
  eval_near: 400
  eval_far: 310
```

**변경 후보**
```yaml
lane:
  y_lo: 290        # 270 -> 290
  y_hi: 410        # 425 -> 410
  eval_near: 390   # 400 -> 390
  eval_far: 320    # 310 -> 320
```

**근거** (테스트영상 428프레임, 2026-08-17 측정)

| 조합 (y_lo~y_hi / near / far) | offset 변화 95%tile | 곡률항 95% | 곡률 변화 95% |
|---|---|---|---|
| 현재 `270~425 / 400 / 310` | 171 px | 167 px | 134 px |
| `290~410 / 400 / 310` | 124 px | 143 px | 104 px |
| **`290~410 / 390 / 320`** | **115 px** | 111 px | **85 px** |
| `270~425 / 380 / 310` | 152 px | 139 px | 89 px |

→ offset 변화 **33% 감소**, 곡률 변화 **37% 감소**

**왜 좋아지나**
1. **샘플 영역 축소**: 위쪽(지평선 근처)은 원근 압축으로 픽셀 노이즈가 크고,
   아래쪽은 차체 가림(검은 원형)에 가깝다. 양 끝을 잘라내면 피팅이 안정된다.
2. **평가행이 샘플 영역 안쪽으로 들어옴**: 다항식은 데이터 범위 밖(외삽)에서
   급격히 발산한다. `eval_near=400`은 `y_hi=410` 바로 앞이라 외삽에 가까웠다.
   390/320은 290~410 범위 안쪽이라 내삽이 된다.

**⚠️ 주의**: 이 측정은 **632×480 테스트영상** 기준이다. 실차 카메라는 640×480이고
장착 각도도 다를 수 있으므로, 실차에서 시각화로 재확인 후 적용할 것.

```bash
# 실차 영상을 녹화해서 같은 비교를 다시 돌릴 것
python3 tools/offline_check.py 실차영상.mp4 --every 15 --viz out/
```

### 1-2. k_curve 를 크게 잡지 말 것 (설계 판단)

시뮬레이션상 최적값은 `1/K_steer = 0.333`이었지만, **현재 0.15로 두는 게 맞다.**

**근거**: 곡률항의 신호 대 잡음비가 낮다.
```
현재 설정:  신호(95%) 167 px / 잡음(변화 95%) 134 px  =  1.25
개선 조합:  신호       111 px / 잡음            85 px  =  1.31
```

시뮬레이션은 **노이즈 없는 이상적 신호**를 가정했다. 실제로는 곡률항이 저 정도로
튀므로, 게인을 크게 주면 **노이즈가 그대로 조향에 실린다.**

노이즈는 `steer.lpf_alpha`(저역통과)와 `steer.rate_limit_per_sec`가 걸러준다.
곡선 오차가 남더라도 게인보다 **필터를 먼저 조정**할 것.

### 1-3. `light.min_ratio` 0.5 → **0.6** (반영 완료)

출발은 되돌릴 수 없고 두 방향으로 다 틀릴 수 있다.

| 실패 | 결과 |
|---|---|
| 조기 출발 (빨간불을 초록으로 오인) | **실격** |
| 늦은 출발 | 기록 손해 |

그런데 **출발 대기 위치가 가장 불리한 조건**이다 — 신호등 박스 ~80px 에서
램프 판독률 68%, conf 0.54 (`perception_analysis.md`). 3번에 1번은 틀린다.

`tools/start_sim.py` 5000회 몬테카를로. "적대적"은 빨간불 오검출이 **전부
GREEN 으로 튄다**는 최악 가정 (실제 YOLO 는 이 정도로 헷갈리지 않는다):

| `min_ratio` | 정상 p95 지연 | 적대적 조기출발 |
|---|---|---|
| **0.5 (기존)** | 0.83s | **48 / 5000** |
| **0.6 (현재)** | 0.97s | **1 / 5000** |
| 0.65 | 1.03s | 3 |
| 0.7 | 1.10s | 1 |

0.6 이 무릎점이다. 조기출발이 48배 줄고 비용은 지연 +0.14s. 그 위로는
안전이 더 안 좋아지지 않고 지연만 늘어난다.

**`light.min_weight` 는 절벽이 있다 — 6.0 을 넘기지 말 것**

| `min_weight` | 결과 |
|---|---|
| 1.0 ~ 3.0 | 정상 (p95 0.87s) |
| 6.0 | 정상이지만 최악 2.0s |
| **10.0** | **3000회 중 1485회 10초 안에 출발 못 함** |

출발 위치는 conf 0.54 라 가중치가 잘 안 쌓인다. "신중하게" 올릴 값이 아니다.

**`window` 도 작다고 빠른 게 아니다** — 10(0.3s)은 p95 1.53s / 최악 3.43s 로
30보다 오히려 나쁘다. 표본이 적어 판정이 흔들린다. 20~45 가 안전 구간.

## 2. 실차에서만 확정 가능한 것

### 2-1. `lane.center_bias_px` — 카메라 장착 편차 보정

**측정 방법**
1. 차를 **트랙 중앙에 똑바로 정지**시킨다
2. `perception_node` 로그의 `offset` 값을 읽는다
3. 그 값을 그대로 `center_bias_px`에 넣는다

```bash
ros2 launch my_perception perception.launch.py
# 로그 예:  offset= +18.3 q1.00 OK   ->  center_bias_px: 18.3
```

**안 하면**: 차선 중앙이 아니라 항상 일정 픽셀 치우친 곳을 따라간다.

### 2-2. `steer.invert` — 조향 방향

**확인 방법**: 차를 들어올린 상태(바퀴 공중)에서 양수 조향 명령을 주고 실제 방향 확인.

```bash
ros2 topic pub --once /xycar_motor std_msgs/Float32MultiArray '{data: [20.0, 0.0]}'
```

| 결과 | 조치 |
|---|---|
| **오른쪽**으로 꺾임 | `invert: false` (그대로) |
| **왼쪽**으로 꺾임 | `invert: true` |

**근거**: `offset > 0` = 트랙 중앙이 화면 오른쪽 = 오른쪽으로 가야 함.
부호 체계는 `lane.py` 주석 참고. 반대면 **차가 차선에서 즉시 이탈**한다.

### 2-3. 조향 게인 3종 — 반드시 이 순서로

> **순서를 지킬 것.** 동시에 만지면 어느 게 효과인지 구분이 안 된다.

#### ① `steer.k_lat` (피드백) — 직선에서

`k_curve: 0`, `k_damp: 0`으로 두고 **직선 구간**에서만 조정.

| 증상 | 조치 |
|---|---|
| 중앙 복귀가 느리다 / 계속 치우쳐 있다 | **키운다** |
| 좌우로 흔들린다 (진동) | **줄인다** |
| 조향이 자주 최대치에 붙는다 | **줄인다** |

**시뮬레이션 기준 참고값** (K_steer=3.0 가정, 초기 +300px 복귀)

| k_lat | 최종오차 | 진동폭 | 조향포화 | 판정 |
|---|---|---|---|---|
| 0.03 | +100.7 px | 8.3 | 0% | 너무 약함 |
| 0.05 | +40.8 px | 6.4 | 0% | 약함 |
| **0.10** | **−2.1 px** | **0.1** | 0% | 기본값 |
| 0.20 | +2.9 px | 0.3 | 2.2% | 양호 |
| 0.40 | −2.3 px | 3.2 | 10.3% | 진동 증가 |
| 0.80 | −16.0 px | 6.8 | **43.6%** | 과함 |

→ **0.10 ~ 0.20 범위**에서 시작

#### ② `steer.k_curve` (선행보상) — 일정 곡률 코너에서

**시뮬레이션으로 이론 확인 완료** (`sim_check.py --k-curve X`, K_STEER=3.0 모델):

| `k_curve` | 곡률40 | 곡률80 | 곡률120 |
|---|---|---|---|
| 0.15 (현재) | +72px | +181px | +270px |
| 0.20 | +54px | +121px | +177px |
| 0.25 | +34px | +72px | +104px |
| **0.333 = 1/K_STEER** | **+0.1px** | **+0.3px** | **+0.7px** |

이론값에서 정상상태 오차가 **완전히 사라진다.** 즉 "코너에서 바깥으로 밀리면
올리고, 안으로 파고들면 내린다"는 절차가 맞다. 오차가 0 근처가 된 그 값이
곧 `1/K_steer` 이고, 그 지점이 유일하다.

> 그런데 **현재값은 일부러 0.15로 낮춰 뒀다.** 위 §1-2 참고 — 곡률 신호의
> S/N 비가 1.3밖에 안 돼서, 0.333 을 쓰면 곡률 잡음이 3배로 증폭돼 조향이
> 떨린다. 시뮬레이터에는 잡음이 없어서 0.333 이 완벽해 보일 뿐이다.
> **실차에서 0.333 부터 시작하지 말 것.** 0.15 에서 시작해 증상을 보며 올린다.


**진단이 명확하다. 부호를 보면 방향을 안다:**

| 증상 | 조치 |
|---|---|
| 곡선 **바깥**으로 밀린다 (오차가 + 로 크다) | **키운다** |
| 곡선 **안쪽**으로 파고든다 (오차가 −) | **줄인다** |
| 직선에서 흔들리기 시작한다 | **줄인다** (노이즈가 실린 것) |

**이론적 배경**
```
offset_ss = curvature × (1/K_steer − k_curve) / k_lat
```
`k_curve = 1/K_steer`가 되면 곡선 정상상태 오차가 0이 된다.
`K_steer`(차량 조향 응답 계수)는 알 수 없으므로 위 증상으로 찾는다.
위 표가 이 식을 수치로 확인해준다.

#### ③ `steer.k_damp` (감쇠) — 마지막

①②를 맞춘 뒤 **남은 떨림**만 잡는다. 조금씩(0.002씩) 올린다.
너무 크면 반응이 둔해진다.

### 2-4. `speed.base` — 낮게 시작

**처음엔 반드시 낮게(8~10) 시작해서 게인을 맞춘 뒤 올릴 것.**
속도가 빠르면 같은 게인이라도 과조향이 된다.

단위 환산 (`speed_weight = 0.08` 기준):
```
speed 12  ->  약 0.96 m/s
speed 27  ->  약 2.16 m/s   (VESC ERPM 상한 10000/4614 = 2.17 m/s)
```
→ **27 이상은 의미 없다.**

고속에서 과조향이면 `steer.speed_gain_ref`에 `speed.base` 값을 넣어
속도 적응 게인을 켠다 (0이면 비활성).

## 4. 미해결 설계 과제

### 4-1. ★ 라바콘 복도 주행 — 골격 구현 완료, 실측 튜닝 대기

**문제**: 라바콘이 좌우로 촘촘히 늘어서 **복도(벽)** 를 이루고, 그 복도가 S자로 굽어 있다.
우측 콘 벽이 흰 실선보다 **안쪽**에 있어서, 페인트 차선 중심을 따라가면
**우측 콘 벽으로 들어간다.**

> ⚠️ README 9장 "하지 말 것"에 *"라바콘 슬라럼 회피 로직 — 라바콘은 차선을
> 안 가린다"* 라고 적어뒀는데 **이 판단은 틀렸다.** 사진 판독 오류였다.
> 콘 벽이 실제 주행 가능 경계이므로 별도 처리가 필요하다.

**구현 상태** (2026-08-17)

| 항목 | 파일 | 상태 |
|---|---|---|
| 복도 중심선 추정 | `my_obstacle/corridor.py` | ✅ 합성 데이터 14/14 (오차 ≤5px) |
| 차선↔복도 융합 | `my_driver/fusion.py` | ✅ 전환 시나리오 6/6 |
| ROS 연동 | `obstacle_node` `/corridor` → `driver_node` | ✅ 배선 완료 |
| **실측 라이다 검증** | — | ⬜ **rosbag 필요** |
| **`px_per_meter` 확정** | — | ⬜ **트랙폭 실측 필요** |

**설계 (구현된 구조)**

차선 추정과 **완전히 같은 구조**다:

```
차선:  YOLO 마스크 → 픽셀 좌표 → polyfit x=f(y) → 두 행 평가   → offset_near, offset_far
복도:  라이다 스캔  → 콘 좌표   → polyfit y=f(x) → 두 거리 평가 → offset_near, offset_far
                                                                    ↑ 출력 형식 동일
```

출력이 같으므로 **제어기(`control.py`)는 하나도 안 고쳐도 된다.**

구현 흐름:
1. `LaserScan` → 직교좌표 (`x = r·cosθ` 전방, `y = r·sinθ` 좌측+)
2. 전방 거리로 구간 분할 (예: 0.3 m 간격)
3. 각 구간에서 좌/우 최근접점 → 중점 `y_center = (y_left + y_right)/2`
4. 중점들을 2차 피팅 `y = a·x² + b·x + c`
5. 두 전방거리에서 평가 → offset 두 개

**단위 변환 (m ↔ px)**: `LaneEstimator`가 이미 **행별 트랙 반폭을 픽셀로 학습**
하고 있다(`self._half`). 실제 트랙 폭을 미터로 재두면
```
px_per_meter = (학습된 픽셀 반폭 × 2) / 실측 트랙폭(m)
```
→ 별도 호모그래피 캘리브레이션 불필요.

**전환 정책 — 스위치가 아니라 가중치 (`fusion.py`)**

"콘 보이면 복도, 아니면 차선"으로 딱 끊으면 전환 순간 목표가 **수십~수백 px 점프**
하고 그게 그대로 조향에 실린다. 그래서 가중치를 시간에 걸쳐 옮긴다.

```
목표 가중치 = f(콘 개수) × (복도 quality / 양측 quality 합) × 2
             ↑ cone_n_lo~hi 사이에서 0→max_corridor_weight
현재 가중치 = 목표로 초당 weight_rate_per_sec 만큼만 이동
```

실측 확인 (`fusion_sim.py`):

| `weight_rate_per_sec` | 전환 시 프레임간 최대 변화 |
|---|---|
| 0.5 | 2 px |
| **1.5 (기본)** | **6 px** |
| 5.0 | 20 px |
| 30.0 | 108 px ← 조향이 튄다 |

**튜닝 순서**

| 증상 | 고칠 파라미터 | 방향 |
|---|---|---|
| 콘 구간 진입 시 차가 휘청 | `fusion.weight_rate_per_sec` | 낮춘다 (1.5→0.8) |
| 콘 구간 진입이 늦어 콘을 스침 | `fusion.cone_n_hi` | 낮춘다 (6→4) |
| 콘 없는데 복도로 새어감 | `fusion.cone_n_lo` | 올린다 (2→3) |
| 복도가 흔들리는데 따라감 | `fusion.min_corridor_quality` | 올린다 (0.4→0.6) |
| 콘 구간에서 여전히 콘 스침 | `fusion.max_corridor_weight` | 올린다 (0.9→1.0) |
| 복도 offset 이 실제와 배율이 안 맞음 | `corridor.px_per_meter` | **아래 계산식** |
| 먼 콘 때문에 곡선에서 오차 | `corridor.x_max` | 낮춘다 (2.2→1.8) |
| 구간 수 부족(`구간N` 로그) | `corridor.bin_size` | 낮춘다 (0.15→0.12) |

**`px_per_meter` — 현재 300.0 은 placeholder다. 반드시 실측으로 대체**
```
px_per_meter = (LaneEstimator 가 학습한 픽셀 반폭 × 2) / 실측 트랙폭(m)
```
이 값이 틀리면 복도 offset 이 통째로 배율만큼 틀리고, 조향 게인이 그만큼
어긋난다. 트랙폭 실측이 **콘 구간 주행의 전제 조건**이다.

**남은 검증**: 합성 데이터만 통과했다. 실측 라이다로 확인해야 한다.
```bash
ros2 bag record /scan /image_raw -o cone_section     # 젯슨, 콘 구간 통과하며
python3 tools/corridor_sim.py --bag cone_section     # (bag 입력은 아직 미구현)
```
현재 `corridor_sim.py` 는 합성 콘 배치만 만든다. rosbag 이 생기면 그때 입력
경로를 붙인다. 그 전까지 `corridor.*` 실측값은 전부 추정치다.

**참고 코드**: `f1tenth_ws.zip`의 `follow_the_gap` 패키지 (라이다 빈틈 탐색)

### 4-2. 지름길 분기 판단

`fsm.enable_shortcut: false`로 비활성 상태. **분기점을 무엇으로 판단할지 미정.**
- 신호등(LEFT 화살표)이 보이는 시점? → 분기점과 신호등 거리 관계를 모름
- SLAM 위치? → 측위 신뢰도 검증 후에만

### 4-3. 2단계 — waypoint 곡률로 선행 감속

지도 생성 → waypoint 기록 → 곡률 계산 → `longitudinal.py`의
`curvature_limit()` 자리에 연결. 도구는 이미 있음
(`my_slam/record_waypoints`, `tools/clean_waypoints.py`).
